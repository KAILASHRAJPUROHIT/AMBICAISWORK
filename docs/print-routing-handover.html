01

The problem, in one sentence

Ornate fires two separate Windows print dialogs per bill — one for the office copy, one for the customer copy — and someone had to sit there picking the right printer for each, every single bill, on every machine.

The two printers have opposite constraints: P1007 already has real letterhead paper loaded but can't duplex, so it only ever needs the raw bill printed straight onto it. 355sdnw can duplex but sits on blank paper, so the customer copy needs the letterhead composited on digitally, front and back, before it prints.

02

How a bill actually routes

Copy order is the only signal available — Ornate doesn't expose which copy is which, so the app infers it from timing (2nd dialog within 20s of the 1st). On relay machines, the P1007 branch copies the raw file to \\PC2\PrintBridge\incoming instead of printing directly, since P1007 is only physically attached to PC2.

06

What actually went wrong

In build order — each one cost real time, so they're worth reading before touching this system again.

Ornate's printer picker is a ListView, not a dropdown

It looks like the classic Win32 print dialog, but the printer list is an icon grid — the same control .NET's PrintDialog uses. Selecting an item needs cross-process memory access (VirtualAllocEx / WriteProcessMemory) into Ornate's own process, since that message type doesn't auto-marshal the way a combo box's does.

NPAV deletes any .exe that PowerShell itself wrote to disk

Silent, no popup, regardless of folder exclusions. The tell was a log line in ZVMON\<date>.log naming POWERSHELL.EXE as the writing process. Fix: deploy every build with robocopy, never Copy-Item.

A second, content-based heuristic hit the standalone watcher exe

Even robocopy-deployed and folder-excluded, a separate background-watcher binary got flagged (spawning hidden child processes reads as a dropper pattern to NPAV). The fix wasn't a better exclusion — it was merging the watcher into the tray app, a binary that had never been touched all session.

Ghostscript draws an invisible full-page white rectangle first

Ornate's captured PDF pages open with an opaque white fill covering the entire page before any content — normal for report-generator output, invisible in any viewer, but it defeats a naive "draw the letterhead behind everything" overlay. Fixed by stripping that specific fill from the raw content stream before compositing.

pypdf silently mishandled that same file; PyMuPDF didn't

pypdf's content-stream reader returned nothing for the exact page PyMuPDF read correctly — no error, just a corrupted merge. Overlay logic now runs entirely on PyMuPDF.

A failed overlay left its output sitting in the watched folder

Which meant the next scan reprocessed it as if it were new input — merged_merged_merged_…pdf, growing one prefix every 3 seconds. Fixed by writing intermediate output outside the watched folder and quarantining any input that fails, instead of leaving it to retry forever.
